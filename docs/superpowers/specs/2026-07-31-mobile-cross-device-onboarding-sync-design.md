# 모바일 크로스 디바이스 온보딩 & 세션 동기화 설계

## 배경 및 문제 정의

Study Tracker는 PC 에이전트 + Chrome Extension으로 PC 사용을 자동 감지하는 구조가 이미 완성되어 있다 (Phase 0~3 완료). Phase 5 로드맵에는 Android/iOS 모바일 지원이 계획되어 있는데, 이 시점에서 다음 우려가 제기되었다:

- 모바일까지 추가되면 사용자는 PC 에이전트, Chrome Extension, 모바일 앱을 각각 설치·로그인해야 하고, 공부할 때마다 여러 기기에서 개별적으로 세션을 시작해야 하는 번거로움이 생긴다.
- 이 프로젝트의 실제 사용 목적상 딴짓(유튜브, 카카오톡, 인스타그램 등)이 PC보다 폰에서 더 많이 발생하므로, 모바일 추적은 "있으면 좋은 기능"이 아니라 순공/딴짓 계산의 정확도에 직결되는 핵심 기능이다. 따라서 설치 자체를 없애는 방향(모바일 미지원, PC 전용)은 선택지가 될 수 없다.

이 설계는 "설치를 없애는" 대신 "설치·로그인의 반복 마찰을 최소화"하는 것을 목표로 한다.

## 목표

1. 최초 계정 생성 이후, 새 기기를 추가하는 과정의 마찰을 최소화한다.
2. 여러 기기에 로그인해 둔 이후에는, 사용자가 매 세션마다 각 기기에서 개별적으로 "시작"을 누르지 않아도 되게 한다.
3. iOS의 OS 제약(개인 앱에 Screen Time API 미승인)을 인정하고, 플랫폼별로 다른 수준의 추적을 명확히 구분한다.
4. 개발 리소스가 1인 개발자 규모임을 감안해, 새로 만들어야 하는 인프라를 최소화하고 기존 구조(device_token, `/api/sessions/active` 폴링, 세션 API)를 최대한 재사용한다.

## 비목표 (Out of scope)

- **모바일로 처음 접근(신규 가입)하는 온보딩 플로우**는 이 설계에서 다루지 않는다. 이번 설계는 "PC에서 계정을 생성한 사용자가 모바일을 추가하는" 시나리오를 전제로 한다. 모바일 우선 온보딩은 추후 별도로 브레인스토밍한다.
- iOS Focus Mode Webhook(Shortcuts 자동화) 연동은 이 설계 범위 밖이며, 기존 Phase 5 항목으로 남겨둔다.
- 배포 인프라(AWS, HTTPS, 도메인)는 기존 Phase 4 범위를 따르며 이 설계에서 다루지 않는다.

## 전체 아키텍처

기존 시스템(Spring Boot 백엔드 + MySQL, PC 에이전트, Chrome Extension, React 웹)에 다음 두 축을 추가한다.

1. **기기 등록**: 계정에 새 기기를 추가하는 최초 1회성 플로우. 신원 인증은 항상 기존 로그인(Google OAuth)을 재사용하며, QR은 순수하게 "앱스토어 또는 안내 페이지로 빠르게 이동시키는 단축키" 역할만 한다.
2. **크로스 디바이스 세션 동기화**: 계정에 등록된 임의의 기기에서 세션이 시작/종료/일시정지되면, 서버가 같은 계정의 다른 활성 기기에 이벤트를 전파해 자동으로 로컬 추적을 맞추도록 한다.

플랫폼별로 추적 방식이 다르므로(PC/Android는 앱·도메인 단위 자동 분류, iOS는 신호 수준), 이 두 축은 공통 인프라로 두고 실제 추적 로직만 플랫폼별로 분기한다.

## 1. 계정 생성 및 로그인

- 인증 방식은 Google OAuth로 통일한다. 기존 `POST /api/auth/register`, `POST /api/auth/login`(이메일/비밀번호)은 Google OAuth 기반 로그인 엔드포인트로 대체한다.
- 웹, iOS(PWA), Android(Native) 모두 동일한 Google OAuth 로그인을 사용한다. Android는 Google Sign-In이 OS 차원에서 지원되어 가장 매끄럽고, iOS PWA와 웹은 표준 OAuth 리다이렉트 플로우를 사용한다.
- 기기 단위 인증(`device_token`)은 기존 구조를 그대로 유지한다: Google OAuth 로그인 성공 후 클라이언트가 `POST /api/auth/device`로 device_token을 발급받는다.

## 2. 기기 등록 (최초 1회)

- 계정 생성/로그인은 PC 웹에서 최초로 이루어지는 것을 기본 시나리오로 한다.
- 로그인 완료 화면(또는 설정 페이지의 "기기 추가" 메뉴)에 QR 코드를 표시한다. QR이 가리키는 URL은 클라이언트가 스캔 기기의 OS를 판별해 분기한다:
  - Android → Play Store 앱 상세 페이지
  - iOS → PWA 안내 페이지("Safari에서 열기 → 공유 버튼 → 홈 화면에 추가" 안내를 포함한 모바일 웹 페이지)
- 설치(또는 홈 화면 추가) 후에는 별도의 페어링 토큰 교환 없이, **동일한 Google OAuth 로그인을 그 기기에서 그대로 수행**한다. 로그인 성공 시 기존 `device_token` 발급 로직이 재사용되며, 추가로 푸시 알림 토큰(FCM, iOS는 FCM 경유 APNs)을 함께 등록한다.
- QR은 "이미 로그인된 기기가 새 기기의 신원을 확인해주는 통로"가 아니라 "앱스토어/설치 페이지로 이동하는 단축키"일 뿐이므로, 별도의 페어링 코드 발급/검증 API가 필요 없다.

## 3. 크로스 디바이스 세션 동기화

이 부분이 반복되는 일상적 마찰을 실제로 제거하는 핵심 메커니즘이다.

- 세션 시작(`POST /api/sessions`), 종료(`PATCH /api/sessions/{id}/end`), 일시정지/재개(`PATCH /api/sessions/{id}/pause`, `/resume`) API가 호출되면, 서버는 해당 이벤트를 같은 계정에 등록된 **다른 모든 기기**에 전파한다.
- **PC**: 기존에 이미 구현된 10초 주기 `/api/sessions/active` 폴링을 그대로 활용한다. PC 에이전트는 상시 실행 중인 프로세스이므로 별도의 푸시 인프라 없이 폴링만으로 충분하다.
- **모바일(Android/iOS)**: OS가 백그라운드 폴링을 강하게 제한하므로, FCM(Android)과 Web Push(iOS, 홈 화면에 추가된 PWA 대상, iOS 16.4+)를 통한 푸시 기반 wake-up이 필요하다. 이벤트 수신 즉시 로컬 추적을 시작/종료한다.
- 종료 이벤트도 시작과 대칭적으로 전파한다 — 한 기기에서 세션을 끝내면 나머지 기기의 추적도 함께 종료된다.
- 이 메커니즘 덕분에 사용자는 어느 기기에서든 세션을 한 번만 시작하면 되고, 다른 기기를 열어서 각각 시작 버튼을 누를 필요가 없다.

### 자동 시작 시 알림

- 다른 기기에서 트리거된 세션 시작/종료로 로컬 추적이 자동 개시될 때, 별도의 확인 절차 없이 즉시 추적을 실행한다.
- 대신 가벼운 토스트/알림으로 고지한다 (예: "공부 세션이 시작되어 추적을 시작합니다"). 이미 사용자 본인이 다른 기기에서 명시적으로 시작한 행위이므로, 재확인을 요구하는 것은 불필요한 마찰이라고 판단했다.

## 4. 플랫폼별 추적 전략

### Android — Native 앱 (Kotlin)

- `UsageStatsManager`를 통해 PC와 동일한 수준의 앱 단위 자동 분류(공부/딴짓/중립)가 가능하다. 이것이 Android를 네이티브로 유지하는 이유다 — 웹으로는 얻을 수 없는 실질적 이점이다.
- `UsageStatsManager` 접근 권한은 일반 런타임 권한이 아니라 별도 설정 화면(설정 > 특별 액세스 > 사용 정보 접근)에서 수동 허용이 필요하다. 온보딩 중 `Settings.ACTION_USAGE_ACCESS_SETTINGS` 인텐트로 해당 화면까지 바로 이동시킨다.
- 백그라운드 유지를 위해 배터리 최적화 예외를 요청한다 (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`), 또는 Foreground Service + 지속 알림 패턴(Strava, Google Fit 등과 동일)으로 우선순위를 유지한다.
- 수집 로직은 PC 에이전트와 유사하게 주기적으로 사용 기록을 조회해 배치 전송한다. 기존 `POST /api/activity-logs`를 그대로 재사용하며 `device_type: ANDROID`로 등록한다.
- FCM 토큰을 등록해 크로스 디바이스 세션 동기화(3번 항목)의 push 수신 채널로 사용한다.

### iOS — PWA (기존 React 웹앱 확장)

- Apple의 Screen Time API(Family Controls 프레임워크)는 개인용 앱에 사실상 승인되지 않으므로, 네이티브 앱으로 만들어도 앱 단위 딴짓 구분은 불가능하다. 즉 네이티브로 개발해도 PWA 대비 얻는 기능적 이점이 없다.
- 따라서 iOS는 별도 네이티브 프로젝트 없이 기존 `study-tracker-web`을 PWA로 확장한다:
  - `manifest.json` + 서비스워커 추가 (홈 화면 추가 지원, 아이콘/스플래시)
  - 모바일 반응형 레이아웃 (세션 시작/종료 컨트롤 중심)
  - Page Visibility API로 세션 진행 중 탭 이탈/복귀를 감지해 "자리 비움" 시간을 기록 (특정 앱 식별은 불가하며, 신호 수준의 추적임을 UI에 "간이 모드"로 명시)
  - Web Push 구독 (iOS 16.4+, 홈 화면에 추가된 상태에서만 동작) — 크로스 디바이스 세션 동기화의 push 수신 채널
- 세션 API는 기존 `/api/sessions`를 그대로 사용하며 `device_type: IOS`로 등록한다.
- 온보딩에서 "Safari 공유 버튼 → 홈 화면에 추가"를 명확히 안내하는 화면이 필요하다 (하지 않으면 푸시 수신이 되지 않고 일반 브라우저 탭으로만 동작함).

## 5. API/데이터 모델 변경 사항

- `devices` 테이블에 push 토큰 컬럼 추가 필요 (`push_token`, 플랫폼별로 FCM 토큰 또는 Web Push subscription 정보를 저장). 기존 `device_token`(인증용)과는 별개의 값이다.
- Google OAuth 로그인 엔드포인트 신설이 필요 (기존 이메일/비밀번호 `register`/`login` 대체).
- 세션 시작/종료/일시정지/재개 API 내부에 "같은 user의 다른 device에 push 발송" 로직 추가 (fire-and-forget, 기존 엔드포인트의 부수 효과로 처리하며 별도의 신규 엔드포인트는 불필요).
- QR 코드 자체는 정적 URL을 클라이언트에서 렌더링하는 것으로 충분하며, 서버 측 API가 필요하지 않다. User-Agent 기반 목적지 분기(Android/iOS)는 프론트엔드 라우팅으로 처리한다.
- `devices.device_type`은 기존 스키마에 IOS/ANDROID 값이 이미 존재하므로 스키마 변경이 필요 없다.

## 6. 기존 시스템과의 재사용 관계

| 재사용 | 신규 |
|---|---|
| `device_token` 발급/인증 구조 | Google OAuth 로그인 |
| `/api/sessions/active` 폴링 (PC) | FCM/Web Push 연동 |
| `/api/sessions`, `/api/activity-logs` 등 기존 세션·로그 API | 세션 이벤트 브로드캐스트 로직 |
| `study-tracker-web` React 코드베이스 (iOS PWA로 확장) | Android 네이티브 프로젝트 (Kotlin, 신규) |
| `devices.device_type` 스키마 | `devices.push_token` 컬럼 |

## 7. 열린 질문 (후속 브레인스토밍 대상)

- 모바일(특히 iOS PWA)로 처음 접근하는 신규 가입자의 온보딩 플로우는 어떻게 설계할 것인가.
- iOS PWA의 백그라운드 동작 제약(브라우저 정책 변경 리스크 포함)이 장기적으로 얼마나 신뢰할 수 있는지 검증 필요.
- Android 네이티브 앱 개발이 이 설계에서 가장 큰 신규 작업량을 차지하므로, 실제 구현 우선순위(Phase 5 내에서 iOS PWA를 먼저 할지 Android를 먼저 할지)는 별도 결정 필요.
